## 3. 测试策略

### 3.1 分层设计

框架按三层拆分，更换被测对象只需修改一处配置：

```
请求层（api_client.py）
  → 统一 base_url、超时、请求封装
数据落库层（db.py）
  → 所有执行结果先入库，成功失败均留痕
报告层（report.py）
  → 从库中读取结果生成统计，按 run_id 隔离批次
```

### 3.2 各类型测试方法

| 类型 | 方法 |
|---|---|
| 接口 | 等价类划分 + 边界值分析 + 参数化（正常 / 边界 / 异常三类目标） |
| 白盒 | 语句覆盖 + 分支覆盖，用 `pytest-cov` 度量，目标 `db.py` 行覆盖率 100% |
| 安全 | 攻击面用例：越权、注入探针、异常输入；设对照组排除假阳性 |
| UI | 显式等待 + 唯一元素定位，失败自动截图 |
| 性能 | 线程池并发压测，统计平均 / P95 / 状态码分布，区分网络错误与接口错误 |

### 3.3 判定原则

- **所有执行结果先入库再判定** —— 避免「先判断成功与否再决定是否入库」导致失败用例静默丢失
- **失败用例同样留痕** —— 报表可回溯每一次失败
- **按 `run_id` 隔离执行批次** —— 报表只统计最新批次，避免历史数据累加

## 5. 风险与应对

| # | 风险 | 影响 | 应对措施 |
|---|---|---|---|
| 1 | **被测 API 是公开服务，可能限流或网络波动** | 用例伪失败，误判为产品缺陷 | 设 `timeout`；网络错误（状态码 0）与接口错误分开统计，不混为一谈 |
| 2 | **CI 环境与本地不一致** | 结果不可复现 | 用 Docker 统一镜像，容器内跑全量；README 写明环境要求 |
| 3 | **用例数被误改导致漏跑** | 假绿（流水线显示成功但实际没跑全） | 设用例数守卫：执行用例少于 33 条直接判失败 |
| 4 | **结果表未按批次隔离** | 统计口径失真（历史数据混入当前批次） | 引入 `run_id`（时间戳 + uuid4 前 6 位），报表只统计最新批次 |
