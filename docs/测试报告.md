## 3. 缺陷统计

| 项 | 数值 |
|---|---|

### 3.1 两条严重缺陷

| 缺陷 | 现象 | 根因 | 修复 |
|---|---|---|---|
| **BUG-001** 结果表未按批次隔离 | 统计数字时大时小：跑了 21 条，报表显示 42 条 | 未给执行批次加标识，历史结果被一起统计 | 引入 `run_id`；`report.py` 用 `ORDER BY id DESC LIMIT 1` 取最新批次；兼容无 `run_id` 的旧数据（标「旧数据：无批次号」） |
| **BUG-002** 结果库相对路径 | 换目录执行后统计为空，但用例明明都跑过 | `DB_PATH` 用了相对路径，从工作目录起算，换目录就写到另一份空库里 | 改为 `Path(__file__).resolve().parent / "test_results.db"`，基于脚本位置而非工作目录 |

### 3.2 四条一般缺陷（摘录）

- 断言过宽：只校验状态码不校验字段值 → 用例失去检出能力
- legacy 表无 `run_id` 列时初始化报错 → 增加 `PRAGMA table_info` 检查 + `ALTER TABLE` 补列
- 失败用例未留痕 → 改为「先入库再断言」
- 网络错误与接口错误混计 → 状态码 0（网络错误）单独统计

## 5. 漏测根因分析

| # | 漏测点 | 根因 | 改进措施 |
|---|---|---|---|
| 1 | **断言过宽导致失去检出能力** | 用例只校验 HTTP 状态码，未校验响应体的具体字段值 → 服务端返回结构变了也判 PASS | 断言必须校验具体字段值（字段存在性 + 值类型 + 关键字段取值），不只依赖状态码 |
| 2 | **统计口径失真**（21 条被算成 42 条） | 结果表未按执行批次隔离，历史数据混入当前统计 | 引入 `run_id` 隔离批次 + 报表只统计最新批次 + 兼容旧数据的分支 |
| 3 | **跨目录执行写错库** | 数据库路径使用相对路径，从工作目录起算 | 改为基于 `__file__` 的绝对路径，不依赖执行时的当前目录 |
